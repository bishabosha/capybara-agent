  1. # Atomic GitHub operations, composed with text editing
  3. The `github` skill implements issue lookup, topic branches, commit/push, draft PRs
  4. and exact-commit CI status. It uses Scala and the JDK HTTP client directly. It has
  5. no Python helper, process sandbox, local test runner or duplicate editing API.
  6. Local editing belongs to `coding`.
  8. Its public interface imports the locally published safe editing API:
  10. ```scala
  11. //> using repository ivy2local
  12. //> using dep "dev.capybara.skills::coding-api:0.1.0-SNAPSHOT"
  13. ```
  15. The directive supplies types for compilation. The manifest separately declares
  16. `requires = Vector("coding")`, so selecting GitHub also supplies a coding context.
  17. The public method declares the authority it needs:
  19. ```scala
  20. def commit(branch: Branch, message: String, paths: Seq[String])
  21. (using files: editing.TextFiles): Branch
  22. ```
  24. The generated safe method has `coding: editing.TextFiles` as a contextual
  25. parameter, so `github.commit(...)` resolves it at the call site. GitHub's factory
  26. and object hold no file capability. Issue lookup, branches, PRs and checks need
  27. only GitHub authority. Without a `TextFiles` context, `commit` fails compilation;
  28. importing its API artifact grants no file access.
  30. ## Configure and run
  32. For the workshop, run setup from the Capybara checkout and select its prepared
  33. workspace. Set the remote repository to your own lab repository:
  35. Run each step separately in the same Bash or Zsh terminal.
  37. **1. Prepare the workshop**
  39. ```sh
  40. ./mill run workshop-setup
  41. ```
  43. **2. Load the GitHub workspace settings**
  45. ```sh
  46. source .agent-runtime/demo-workspaces/github.env
  47. ```
  49. **3. Configure the remote repository**
  51. ```sh
  52. export CAPYBARA_GITHUB_REPOSITORY=YOUR-ACCOUNT/YOUR-REPOSITORY
  53. export CAPYBARA_GITHUB_BASE=main
  54. ```
  56. Provide `CAPYBARA_GITHUB_TOKEN` through your secret manager or a hidden prompt.
  57. For zsh:
  59. ```sh
  60. read -rs 'CAPYBARA_GITHUB_TOKEN?GitHub token: '
  61. export CAPYBARA_GITHUB_TOKEN
  62. ```
  64. Use a fine-grained or GitHub App token scoped to the repository. Grant Contents
  65. write, Issues read, Pull requests write, and optionally Checks/Commit statuses
  66. read for `checks`. Tokens never belong in snippets, manifests, files, PR bodies
  67. or model messages. No method returns a token.
  69. The local clone supplies text; the API publishes only the named files. It does
  70. not run `git`, hooks, shell commands or tests. Keep real credentials outside the
  71. coding workspace, because a generic read grant intentionally releases ordinary
  72. file contents. The GitHub client additionally rejects the actual token, several
  73. direct encodings, common token patterns and the synthetic lab canary in outgoing
  74. files/metadata and issue text. Those checks are not universal string tainting.
  76. ## One composed tool call
  78. ```json
  79. {
  80. "universes": ["coding", "github"],
  81. "scala_code": "..."
  82. }
  83. ```
  85. The legacy `universe` field still supports single-skill calls. For the developer
  86. CLI, use comma-separated skill directories or names:
  88. ```sh
  89. ./mill run skill-run --skill coding,github \
  90. --file examples/snippets/github-lab.scala
  91. ./mill run skill-transcript --skill coding,github \
  92. --file examples/snippets/github-lab.scala
  93. ./mill run skill-ide --skill skills/github
  94. ```
  96. Publish local safe APIs directly with `./mill run skill-publish --skill github`.
  97. It publishes coding first, then GitHub, and prints their dependency directives.
  98. Implementations remain separate installed skills; no factory runs during publication.
  100. IDE preparation publishes required APIs first. The preview shows all injected
  101. capabilities; runtime snippet bodies still compile separately in safe mode.
  102. `skill-transcript` only renders commands and does not execute them.
  104. The example assumes a clone of the word-count starter and issue #1. It creates
  105. `capybara/issue-1`, edits local source through `coding`, publishes that one file
  106. and opens a draft PR. Choose a fresh topic name for another run. With production
  107. wiring it performs real remote writes. Automated tests use a local GitHub HTTP
  108. fixture and synthetic credentials.
  110. ```scala
  111. puts(github.lookupIssue(1))
  112. val topic = github.createBranch("capybara/issue-1")
  113. coding.edit("src/word-count.mjs") { text =>
  114. text.replace("return text.split(' ').length;",
  115. """const clean = text.trim();
  116. return clean === '' ? 0 : clean.split(/\s+/u).length;""")
  117. }
  118. val pushed = github.commit(topic, "Fix whitespace", Seq("src/word-count.mjs"))
  119. puts(github.createPullRequest(pushed, "Fix whitespace", "Fixes #1"))
  120. puts(github.checks(pushed))
  121. ```
  123. For an LLM run, set the same environment and ask the agent to use coding and
  124. GitHub together. It can list issues, inspect requirements, edit source, publish a
  125. topic branch and report the draft PR/CI result. Functional verification can be a
  126. separate task or skill; it is not embedded in the text or GitHub interfaces.
  128. ## Capability boundary
  130. The generated safe method receives separate `coding`, `github` and `output`
  131. parameters. A pure edit callback cannot retain any of them:
  133. ```scala
  134. coding.edit("README.md")(text => { puts(text); text })
  135. coding.edit("README.md")(text => github.lookupIssue(1).body)
  136. ```
  138. Both fail capture checking. Calling GitHub outside that callback is authorized
  139. by the supplied GitHub capability. Safe mode rejects direct environment, process
  140. and reflective field access in the regression cases. Trusted factories are
  141. marked `@caps.rejectSafe`.
  143. `createBranch` accepts only a `capybara/` topic name and never overwrites an
  144. existing branch. `commit` checks the exact expected head, uploads selected local
  145. text and advances the ref without force. A stale `Branch` returns
  146. `BRANCH_CHANGED`; inspect it with `branch(name)` before deciding what to do.
  147. PR creation checks the exact head, creates a draft and reuses an existing exact
  148. head/base PR. It cannot merge or promote it. The client rejects redirects,
  149. disables proxies and uses the configured GitHub repository at a fixed origin.
  150. HTTP error bodies and original exceptions never enter tool output.
  152. API importing supplies types, not credential values. The installed skill graph
  153. and manifest control which runtime capabilities are constructed. Pure callbacks
  154. control retained references, not the confidentiality of arbitrary text. Existing
  155. remote CI remains repository-controlled and runs independently of this harness.
  157. Run `GitHubSkillSuite` and `SkillCompositionSuite` through Metals MCP. They test
  158. real HTTP serialization, local API publication, safe API delegation, independent
  159. editing/GitHub operations, cross-skill capture failures and credential rejection.
  160. No live GitHub repository is mutated by these tests.
